# Labije Cab : déploiement

Prérequis : Node 22.18 ou plus récent (le banc de vérification utilise `node:sqlite`), un compte Cloudflare (`npx wrangler login`).

**Le site est un Worker Cloudflare qui sert aussi ses fichiers statiques** (`wrangler.toml` : `main = "dist/_worker.js/index.js"`, bloc `[assets]`). Ce n'est plus un projet Pages : Cloudflare ne les crée plus (« Pages fait désormais partie de Workers »). Le build écrit `dist/.assetsignore` (copié depuis `public/.assetsignore`), qui garde le code du Worker hors des fichiers publics.

```bash
npm install
npx wrangler d1 create labije-cab                                  # reporter database_id dans wrangler.toml
npx wrangler r2 bucket create labije-cab-fichiers                  # fichiers : ne PAS activer le domaine public ni r2.dev
npx wrangler d1 migrations apply labije-cab --local                # migrations, base locale
npx wrangler d1 execute labije-cab --local --file=seeds/demo.sql   # jeu de démonstration, local seulement
npm run dev                                                    # http://localhost:4321
npm run build && npx wrangler dev --var MAIL_DRIVER:console             # contrôle du build, http://localhost:8787
npx wrangler d1 migrations apply labije-cab --remote               # migrations, base de production
npx wrangler secret put SCW_SECRET_KEY                         # secrets du Worker du site ; idem SCW_PROJECT_ID, MAIL_FROM
npx wrangler deploy                                            # déploiement du Worker et de ses fichiers (après npm run build)
npx wrangler deploy --dry-run                                  # contrôle sans rien publier
```

- Variables d'environnement : `MAIL_DRIVER=scaleway` (et `SCW_REGION` si autre que `fr-par`) sous `[vars]` dans `wrangler.toml` ; les clés (`SCW_SECRET_KEY`, `SCW_PROJECT_ID`, `MAIL_FROM`) en secrets, comme ci-dessus.
- Ne jamais lancer `seeds/demo.sql` avec `--remote` : données fictives.
- Sous `npm run dev`, `MAIL_DRIVER` vaut `console` : le lien de connexion s'affiche dans le terminal. Sur un build servi par `wrangler dev`, le pilote par défaut est `scaleway` : ajouter `--var MAIL_DRIVER:console` pour lire le lien. Ne jamais poser `MAIL_DRIVER=console` en production : le pilote `console` lève une erreur dès que l'hôte de la requête n'est ni `localhost` ni `127.0.0.1`. Posé par erreur en production, il n'envoie donc plus aucun courriel (panne visible, journalisée sans le lien) au lieu d'écrire des liens de connexion encore valables dans les journaux de Cloudflare.
- Premier tenant de production : `npx wrangler d1 execute labije-cab --remote --command "INSERT INTO tenant (id, nom, domaine, cree_le) VALUES ('tnt_1', 'Nom', 'www.exemple.fr', '2026-01-01T00:00:00Z')"`.
- Console de l'éditeur (`/admin`, rôle éditeur) : elle crée un cabinet sans SQL (le « premier tenant » ci-dessus ne sert plus qu'à amorcer le compte éditeur). Domaines personnalisés (Cloudflare for SaaS), appelés côté serveur seulement (secrets et variables du Worker du site, `labije-cab`) : `npx wrangler secret put CF_API_TOKEN` (jeton limité à la zone, droit « SSL and Certificates : Edit »), puis sous `[vars]` : `CF_ZONE_ID` (la zone qui porte les « custom hostnames ») et `CF_CNAME_CIBLE` (l'origine de repli que le cabinet vise par CNAME). Sans le jeton, la console le dit sur la fiche du cabinet et tout le reste fonctionne : les noms d'hôte se déclarent, mais rien n'est validé chez Cloudflare. Un nom d'hôte n'ouvre un cabinet qu'une fois validé. Une fois validé, il peut devenir l'adresse du site public et/ou de la connexion et de l'espace du cabinet (fiche du cabinet › « Domaines » › « Adresses du cabinet » ; réglages `hote_public` et `hote_espace`, sans migration) : les autres adresses du cabinet redirigent (301 pour le site, 302 pour la connexion), aucune redirection en local ni pour POST, API, fichiers, `robots.txt` et plan du site ; voir `livraison/DOSSIER-LIVRAISON-PRODUCTION.md`, section 3. Pour un essai local, `CF_API_URL` remplace l'adresse de l'API.
- Le premier cabinet créé par la console reçoit son lien de première connexion par le pilote de mail : en local, utiliser l'hôte `127.0.0.1` (le pilote `console` refuse tout autre hôte) et `--var MAIL_DRIVER:console`.
- Traitement quotidien (lot 12) : un Worker à part, `wrangler.cron.toml`, avec UN Cron Trigger (`0 3 * * *`, 03:00 UTC). Il reste séparé du Worker du site (`wrangler.toml`) : une tâche planifiée ne se mêle pas au code qui répond aux visiteurs. À faire une fois, côté Cloudflare : reporter `database_id` et `CF_ZONE_ID` dans `wrangler.cron.toml`, `npx wrangler deploy -c wrangler.cron.toml`, puis les secrets du Worker (`npx wrangler secret put SCW_SECRET_KEY -c wrangler.cron.toml`, idem `SCW_PROJECT_ID`, `MAIL_FROM`, `CF_API_TOKEN` : ce sont les six courriels de sortie — quatre pour l'essai, deux pour une résiliation — et la libération du domaine à la suppression des données (J+75 de l'essai, J+30 d'une résiliation)), puis `npx wrangler d1 migrations apply labije-cab --remote` (migrations 0010 à 0013). En local, `npx wrangler d1 migrations apply labije-cab --local -c wrangler.cron.toml` crée la même base que `npm run dev` ; ajouter `--var MAIL_DRIVER:console` à `wrangler dev` pour que les six courriels de sortie s'écrivent dans la console. Dans le tableau de bord : Workers & Pages → `labije-cab-traitement` → Settings → Triggers doit montrer le cron ; Settings → Variables doit montrer `DB` et `FICHIERS`. Essai : `npx wrangler dev -c wrangler.cron.toml --test-scheduled`, puis `curl "http://localhost:8787/__scheduled"`. Le traitement est idempotent : le rejouer à la main ne duplique rien.

- Cours de marché (écran Actus du gestionnaire) : récupérés chaque nuit par ce même Worker (travail « cours » du traitement quotidien), depuis Alpha Vantage avec une clé gratuite (25 appels par jour, tous cabinets confondus). Un appel par symbole rend une trentaine à une centaine de séances, toutes rangées dans la table `cours` : c'est l'historique des courbes du bloc « Marchés », dès le premier passage. L'ensemble suivi est l'union dédoublonnée des symboles de tous les cabinets (cinq par défaut : CAC.PAR, SPY, QQQ, EUR/USD, Brent) ; au-delà de 25 symboles, le surplus n'est pas appelé et un incident le dit. **Le secret `COURS_API_KEY` se pose deux fois** : `npx wrangler secret put COURS_API_KEY -c wrangler.cron.toml` (le Worker du traitement) et `npx wrangler secret put COURS_API_KEY` (le Worker du site, qui s'en sert comme filet : à l'ouverture de l'écran Actus, il récupère seulement ce que la nuit n'a pas fait, sans rappeler ce qui l'a été). Sans clé, rien n'est appelé : un incident « Cours : clé d'API absente » dans la console et un message sur l'écran. Un symbole en échec écrit un incident et n'arrête pas les autres. En local : `COURS_API_URL` redirige les appels vers un serveur factice.
- Les seuls courriels automatiques du produit vers un cabinet sont les quatre de l'essai (J+38, J+45, J+68, et l'avis tardif qui remplace J+68 quand aucun avis n'est jamais parti). Le reste — bon à émettre, remise à revoir, suppression en attente — arrive à l'éditeur dans les incidents de la console (`/admin/incidents`), jamais par courriel.

## Domaines du site

Le domaine du produit se branche sur le **Worker du site** : Cloudflare → Workers & Pages → `labije-cab` → Settings → Domains & Routes → Add → Custom domain. Les domaines des cabinets (noms d'hôte personnalisés) restent gérés par la console `/admin` et Cloudflare for SaaS, comme décrit plus haut. L'adresse `labije-cab.<compte>.workers.dev` est celle de repli : un cabinet n'y est reconnu que si son nom d'hôte y est déclaré.
